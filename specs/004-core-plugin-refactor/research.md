# Research: Core / Plugin Architecture Refactor (0.9.8)

**Date**: 2026-09-28
**Inputs**: [feature specification](./spec.md), the project constitution and its canonical provider-neutral baseline, current source and tests, and the [implementation roadmap](https://app.notion.com/p/34f33dd99fc8812ea5f2eae262910ab3).

## 1. Model exception profiles

**Decision**: Add an explicit `capability_exceptions` list to each first-party exact-model registry entry. Maintain a versioned catalogue of model-dependent capabilities derived from the existing baseline, including chat and streaming modes, application tools and tool-choice variants, structured output, image and document forms, reasoning controls/events, continuation, usage, refusal, and incomplete outcomes. Each listed exception names its canonical capability, a stable value-independent `behavior_id`, and verified provider limitation and adapter behavior. Reuse `pass`, `ignored`, `rejected_before_transport`, and `none_falls_back_to_minimum`; add a provider-specific ID only when the shared outcome and structured metadata cannot express the behavior. Exact values and limits remain authoritative in dedicated registry fields. An unlisted capability keeps its baseline-positive check. A successful package workaround remains a visible exception with `behavior_id: "pass"` and follows the same positive E2E route; package unit or integration tests verify the normalization. Do not infer exceptions from organization, package placement, model-name prefix, or another model's profile.

**Rationale**: `ModelSpec` currently stores limits, pricing, reasoning, and request rules, but no baseline exceptions (`src/llm_api_adapter/llm_registry/llm_registry.py`). Existing E2E loops already enumerate exact models, while feature deselection is organization-wide (`tests/e2e/conftest.py`). Per-model exception lists let each exact model run the baseline-positive scenario by default and select a specific exception check only where needed. Repository inspection found 57 registered model entries in nine organization catalogues (43 built-in, 14 external). The constitution remains the sole baseline; this feature does not create separate admission rules.

**Compatibility boundary**: First-party bundled and organization-package catalogues must have an explicit validated exception list on every exact model for the 0.9.8 release; the list may be empty. An older third-party plugin may continue to register and serve requests without a new plugin API requirement. Its missing capability profile is an error when profile-based conformance/E2E selection or release certification is requested. Shared transport, facade, message/error normalization, pricing, request-rule fidelity, and cleanup invariants remain mandatory checks and cannot be excepted by a model profile.

**Alternatives considered**: Copying organization-wide feature flags to each model would preserve false assumptions. Rejecting every legacy third-party plugin at registration would change the external plugin contract. Treating a missing flag as false would hide missing tests. All three were rejected.

## 2. Shared scenario selection and evidence

**Decision**: Define one deterministic mapping from canonical capability identifiers to baseline-positive shared scenarios and from declared non-`pass` `(capability_id, behavior_id)` pairs to documented exception scenarios. An unlisted capability or a `pass` exception selects its positive scenario; other exceptions select their matching replacement scenario. Fail validation for a missing profile, unknown/duplicate/always-on exception, missing or malformed behavior ID, or missing/duplicate route. Keep pytest node IDs in the test catalogue rather than runtime metadata, and never infer a route from the prose `behavior` field. Mistral PDF through OCR is a `pass` exception whose public contract follows the shared positive PDF route; package tests verify OCR routing and costs. Make common cross-cutting scenarios unconditional for the selected lane.

**Rationale**: `tests/e2e/conftest.py` currently deselects `@e2e_feature` tests by organization-level set inclusion, while other common tests already iterate exact models. `tests/unit/conformance/test_portable_profile_matrix.py` has a separate hand-maintained terminal-outcome map. These sources can drift. `tests/e2e/test_async.py` also has outcome-driven skips for malformed structured results; when no exception is declared for a model, the baseline-positive check must fail on that behavior.

The prose `behavior` field cannot select evidence deterministically. Mistral PDF input succeeds through OCR despite a provider limitation, so its `pass` exception takes the baseline-positive route while package tests verify the OCR conversion. Packages that reject PDF before transport declare a different behavior ID and select rejection evidence. An explicit `pass` code keeps these cases visible and avoids a nullable behavior ID.

**Lane boundary**: `.github/scripts/select_e2e_lanes.py` continues to choose the affected provider lane by changed paths. `.github/workflows/ci-dev-release.yml` continues to own separate jobs, exact candidate installation, and one-provider credential access. Capability data selects scenarios *inside* a lane and never grants access to a provider secret or changes which paid lane runs.

**Alternatives considered**: Growing the organization-level `supported_features` sets or placing test node IDs in provider packages would duplicate model facts and couple registry releases to test names. Both were rejected.

## 3. Automatic cache input and pricing

**Decision**: Account only for provider-managed cache components that can occur automatically during an ordinary adapter request and whose quantities the provider reports. Add optional independently verified `cache_read_input_per_1m` and `cache_write_input_per_1m` rates to applicable exact-model pricing tiers. Retain `cached_tokens` as the backward-compatible cache-read/cache-hit count in common `Usage` and add a separate optional cache-write count. Preserve existing `ChatResponse.cost_input` as the combined ordinary-plus-read-plus-write input charge, `cost_output` as output charge, and `cost_total` as a complete total only when every incurred component is known and priceable. Do not add public cache-control operations, cache-mode metadata, TTL selection, cache resources, or storage accounting. Use the full reported input-token count to select a tier before splitting it into ordinary, read, and write portions. A model with a distinct automatic cache rate and missing, malformed, or inconsistent component split has unknown input and total cost; independently confirmed output cost may remain available.

**Rationale**: Core `PricingTier` has only ordinary input/output rates, and Core `Usage` has no cache fields. Z.ai, Kimi, and DeepSeek already report `usage.cached_tokens` through package-specific subclasses and calculate cache-read costs separately. Kimi's standard Chat Completions response can also report `prompt_tokens_details.cache_write_tokens`, so one generic cached bucket cannot represent its complete input accounting. Kimi's registry has a separate `cache_pricing` block; Z.ai uses `registry/cache_pricing.py`. Generalizing only verified automatic component rates removes this duplication while preserving the public aggregate cost fields. Leaving unsupported opt-in cache features absent avoids turning the registry into a catalogue of provider features the adapter does not exercise. Tests in Z.ai and Kimi currently expect a full-rate total without a cache split; that expectation conflicts with the 0.9.8 requirement not to assume a cache miss and must be updated explicitly.

**Non-static rates**: DeepSeek's peak/off-peak rate selection depends on request-dispatch time (`packages/organizations/deepseek/src/llm_api_adapter_deepseek/registry/cache_pricing.py`). Keep that selection package-owned and pass the selected verified rates through shared accounting where possible; do not encode a time-dependent rate as one static registry value. Existing tier boundaries and currency behavior remain authoritative.

**Alternatives considered**: Recording every provider's documented cache modes and rates was rejected because 0.9.8 does not send cache-control requests and unused metadata would not describe adapter behavior. Treating missing cache usage as zero would fabricate component absence. Falling back from cache read or write to the ordinary or other cache rate would invent a price. Applying one cached rate to all input would double-discount or misprice writes. Flattening DeepSeek to a static rate would misprice time-dependent requests. A new public per-component cost field is deferred because 0.9.8 can report confirmed quantities and correct aggregate costs with the existing response cost fields.

## 4. External organization metadata consistency

**Decision**: Keep `KNOWN_ORGANIZATION_PACKAGES` as the Core source for known external organization and distribution names. Derive safe test-profile metadata from it where practical, and add a deterministic repository check that compares that mapping with Core extras, each package's manifest and entry point, E2E profile names/distributions, and the CI lane selector. Fail with the organization and mismatching source. Leave workflow jobs, version extraction, publication boundaries, and secrets explicit per distribution.

**Rationale**: The six external organizations (`mistral`, `xai`, `qwen`, `kimi`, `deepseek`, `zai`) currently appear separately in `organization_registry.py`, `pyproject.toml`, `tests/e2e/conftest.py`, `.github/scripts/select_e2e_lanes.py`, package manifests, and `.github/workflows/ci-dev-release.yml`. The current values align, but no single deterministic check detects a new missing package or changed name. Static package metadata cannot safely be generated from runtime Core imports without changing build behavior.

**Alternatives considered**: Generating CI jobs or package metadata from a runtime registry would entangle build, security, and release policy. Accepting duplicate strings without a drift check would leave the reported failure mode intact. Both were rejected.

## 5. Verification and release scope

**Decision**: Run focused registry, response, accounting, conformance, metadata, and lane-selection tests first, then the credential-free unit and mocked-integration suite across Python 3.10–3.14. Check E2E collection without making provider calls. Paid live E2E remains in the established maintainer-controlled post-publish lanes against exact TestPyPI candidates. Release Core 0.9.8 only after backward compatibility and the common conformance gate are satisfied; keep organization package versions and publication jobs independent.

**Rationale**: The constitution requires deterministic PR checks and segregated paid E2E. `.github/workflows/ci-dev.yml` already runs the Python matrix and a canonical 3.10 coverage floor of 90%. The existing release workflow already owns provider-specific secrets and candidate installation.

**Remaining work**: Verify each declared exact-model exception against authoritative documentation. T035 completed the automatic-cache source audit; T033/T039 must stay within its documented ordinary-request fields and rates. Map every shared scenario to its baseline capability or cross-cutting invariant, and update affected package expectations. The public missing-count compatibility choice remains unresolved: FR-013 promises no caller changes, while the proposed `None` correction requires callers doing arithmetic to adapt. Resolve that constitution-level conflict before changing `Usage`.
